## ADR-009 — Copernicus Data Access: Decoupled Catalog Discovery, Download Auth & Credential Accounting
**Conflict:** "Copernicus Data Space" was generically referenced without separating catalog search, download protocols, or authentication mechanisms. Furthermore, assuming Sentinel Hub OAuth client credentials (`sh-...`) automatically authorize CDSE OData archive downloads conflates two distinct provider authorization surfaces.
**Resolution:**
1. **Separation of Services**:
   - **Catalog Discovery**: STAC API (`https://catalogue.dataspace.copernicus.eu/stac`) or OData Catalog (`/odata/v1/Products`) for querying Sentinel-2 L2A footprints, cloud cover, and acquisition metadata. Catalog search operates independently of download tokens.
   - **Download / Retrieval**:
     - *Route A (Sentinel Hub Process API)*: Area-limited multi-spectral band extraction via `sh.dataspace.copernicus.eu/api/v1/process`, authenticated via Sentinel Hub OAuth2 client credentials (`sh-...`).
     - *Route B (CDSE OData Download)*: Full product ZIP/SAFE archive downloads via `/odata/v1/Products({id})/$value`, requiring CDSE Keycloak bearer tokens.
2. **Credential Presence vs. Authentication vs. Authorization**:
   - Recording credential presence (e.g., `Client_ID` / `Client_secret` configured in `.env`) must be strictly decoupled from token acquisition (successful authentication) and from download entitlement (successful authorization).
   - Presence of `sh-...` credentials certifies Sentinel Hub API credential presence only; it does *not* prove CDSE OData downloads work.
   - Runtime and preflight checks (`doctor.py`) must report `credential_present`, `catalog_discovery_accessible`, `token_exchange_success`, and `download_authorized` as separate, explicit facts.
**Status:** Reflected in settings.py, scripts/doctor.py, task.md Phase 3.

## ADR-013 — Confidence score schema & Missing-Factor Policy (Anti-Renormalization)
**Conflict:** Confidence formula was unspecified; risk that missing quality factors inflate confidence scores through dynamic weight renormalization over only available factors.  
**Resolution:**
1. **Anti-Renormalization Policy**:
   - Total base weights sum to 1.0 ($\sum_{i \in \text{all}} w_i \le 1.0$).
   - Dynamic weight renormalization (dividing by the sum of available weights) is strictly **PROHIBITED**. Normalizing over available factors would allow a high single-factor signal (e.g., model raw probability = 0.95 with base weight 0.10) to expand to 100% of the score when registration, cloud, or temporal evidence is missing.
   - Missing or unavailable factors contribute exactly **0.0** to the score numerator and their weight remains unallocated. Missing evidence therefore acts as an inherent penalty, strictly capping the maximum possible confidence at $\sum_{i \in \text{available}} w_i$.
   - Any score evaluated with missing factors reports `complete_evidence: false` and lists every missing factor name in `missing_factors`.
2. **Schema**:
   - `{score: float, calibrated: false, complete_evidence: bool, factors: list[{name, value, weight, available}], missing_factors: list[str], rejection_reasons: list[str], weights_version: str}`.
**Status:** Reflected in core/qc.py, task.md Phase 8, unit tests.
